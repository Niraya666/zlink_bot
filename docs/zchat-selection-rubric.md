# ZChat 副驾选人 rubric（判断 agent 设计草案）

> 状态：设计草案（2026-08-03），尚未实现
> 用途：给一个「判断某人是否适合这场 coffee chat」的 agent 提供评分框架
> 数据来源：zlink 报名数据（`node cli.js export <slug>` 的 JSON 输出）

## 0. 最重要的一条

**不要设计成给个人打分排序，应该是选组合。**

6 个人如果全是「被裁的 Junior」，讨论会很单薄；有 2 个带过人的 Mentor
+ 2 个正在 GAP 的 + 1 个转型中的 + 1 个行业观察者，张力才出得来。

**个人分最高的 6 个人，不等于最好的 6 人组合。** 任何只做个人排序的
rubric 都会系统性地选出同质化的一桌人。

## 1. 个人层：5 个维度

| 维度 | 分档 | 数据来源 |
|---|---|---|
| **议题亲历度** | 0 只是感兴趣 / 1 旁观过（同事经历过） / 2 亲历过一类 / 3 亲历且仍在其中，张力未解 | `background` |
| **具体性** | 0 全是抽象观点与行业黑话 / 1 有例子但泛泛 / 2 有具体场景、时间、决策 / 3 还包含自己的判断失误与反思 | `background` + `bring_topic` |
| **未解张力** | 0 已有结论、来布道 / 1 有困惑但表述模糊 / 2 有清晰的、真的没解决的问题 | `bring_topic` |
| **贡献面** | 0 只想吸收 / 1 能给单一视角 / 2 能给别人接不住的视角 | `unique_angle` + `background` |
| **可靠性** | 0 有鸽记录 / 1 无记录 / 2 参加过且交过小作文 | ⚠️ 见 §3 |

### 为什么不做成结构化字段

「具体性」「未解张力」这两维**故意不设字段**——让判断 agent 直接读
`background` / `bring_topic` 的原文。LLM 读自由文本比读结构化标签准得多，
而且多一个字段就多一轮对话，报名完成率会掉。

## 2. 组合层：一条硬约束

> 最终 6 人中至少覆盖 **3 种不同视角**，且同一视角不超过 3 人。

视角标签（由判断 agent 从 `background` 自行归类，不额外问参与者）：

- **带过人的** —— Mentor / Team lead，对培养成本有实感
- **GAP 亲历者** —— 主动暂停或被动失速，有真实的空窗期体验
- **转型新人** —— 刚入行或正在换赛道，直接撞上练级路径消失
- **行业观察者** —— 关注 AI / 教育 / 就业结构变化，带案例而非结论

建议流程：先按个人分排序取候选池（比如前 12 名），再在池内按组合约束挑 6 人，
而不是直接取前 6。

## 3. 「可靠性」维度的数据从哪来

**这一维不能问参与者**——没人会说自己鸽过。它必须来自组织者侧的记录。

现成的出路：如果后续几期 ZChat 都走 zlink，`data/bot.sqlite` 会自然积累历史。
`users` 表虽按 `event_id` 隔离，但**同一个 `wechat_uid` 跨活动可查**：

```sql
SELECT event_id, status, created_at
FROM users
WHERE wechat_uid = ?
ORDER BY created_at;
```

判断 agent 可以据此得出「来过几次、完成过几次」。
**这是跑第二场之后自动获得的能力，现在不需要做任何事。**

第一场只能把这一维留空，或统一按 1（无记录）处理。

## 4. 当前字段够不够

个人层的前四维都有数据支撑：

| 维度 | 覆盖情况 |
|---|---|
| 议题亲历度 | ✅ `background` |
| 具体性 | ✅ 从 `background` / `bring_topic` 原文判断 |
| 未解张力 | ✅ `bring_topic`（可选，可能为空） |
| 贡献面 | ✅ `unique_angle`（可选，可能为空）+ `background` |
| 可靠性 | ❌ 见 §3，需跨期数据 |

两个可选字段可能为空——这本身也是信号：**能把「没想明白的问题」和「独特视角」
说清楚的人，通常就是这场讨论要的人**。判断 agent 应把「空」当作弱负信号，
而不是缺失值跳过。

## 5. 实现建议（如果真要做）

不要做成 zlink 的一部分。报名数据导出后单独跑即可：

```bash
node cli.js export zchat-23 > signups.json
```

判断 agent 读这份 JSON，输出候选池 + 组合建议 + 每人一句理由，
最终名单仍由组织者定。**agent 给依据，不给决定。**

## 6. 待验证

这套 rubric 完全没有真实数据检验过。第一场跑完后应该回头看：

- 哪一维在实际数据上最没有区分度（可能可以删）
- 哪一维判断 agent 最没把握（可能需要补字段）
- 组合约束是否真的带来了更好的讨论（问参与者的复盘小作文）
