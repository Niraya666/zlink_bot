# 公网暴露方案：抉择与三步走

> 状态：方案已定，待执行（2026-07-29）
> 前置：`docs/multi-binding-findings.md`（多绑定可行性，核心项待验证）
> 场景：微信群约 300 人的活动报名，公开报名（非邀请制）

## 1. 为什么需要公网

两个硬约束叠加：

- 二维码有效期 **约 120 秒**（实测，见 findings §2）
- 每个参与者需要**属于自己的独立二维码**（iLink 是一对一绑定模型，findings §1）

⇒ 码必须在参与者点开的那一刻现场生成，而生成动作在持有绑定的进程里
⇒ 参与者设备到该进程之间必须有可达路径

## 2. 分发方式：群里发一个固定链接即可

常见误解是"要给 300 个人分别发二维码"。实际上：

```
群里发一个固定页面链接（比如 https://join.example.com/）
        ↓ 每个人各自点开
   页面为该访客当场生成一张新码 / 一个可点链接
        ↓ 点击（微信内）或扫码（桌面端）
   ClawBot 出现在他自己的微信里 → 开始对话
```

**链接静态，码每人独立**，因此 120 秒的有效期不构成分发障碍——计时从他点开那一刻才开始。

### 微信内可以直接点，不必扫

二维码内容本质是 URL：

```
https://liteapp.weixin.qq.com/q/7GiQu1?qrcode=<每人不同>&bot_type=3
```

域名是 `weixin.qq.com`，所以在微信内置浏览器里给一个 `<a href>` 让他点，比"显示二维码 → 长按识别 / 换设备扫"顺畅得多。**主路径应设计为微信内点击**，二维码作为桌面端回退。

## 3. 关键纠正：备案与「隧道 or 云主机」无关

备案的触发条件是**服务器在中国大陆**。因此：

| 方案 | 是否需要备案 |
|---|---|
| Cloudflare Tunnel → 家里的 Mac mini | 不需要 |
| **境外**云主机（香港 / 新加坡）+ 境外注册域名 | **也不需要** |

两者都能免备案，所以备案不是决策依据。**真正的分歧点是「进程跑在哪台机器上」。**

> ⚠ 别指望 Cloudflare 加速国内访问。其中国节点需企业版 + 京东云合作，
> **而那条路反而要求备案**。免费版国内流量会绕到香港/日本节点。
> Cloudflare 在这里提供的是域名、TLS、免公网 IP，不是国内速度。

### 已排除：小程序

调研过（含体验版路线），结论是方向相反：

- 体验版仅限**预先按微信号登记的体验成员**，未认证个人号上限 **15 人**、有效期 **14 天**
- 体验版开调试模式确实能忽略域名与证书校验（可免备案），但 15 人上限对 300 人场景无意义
- 更关键：体验成员要预先知道微信号，**而收集信息正是这个 bot 的目的**，逻辑自相矛盾
- 小程序**正式版**对域名要求比 H5 更严：未备案域名**直接驳回审核**

小程序唯一有价值的用法是「B 步的小规模真实测试」，不是最终方案。

## 4. 抉择表

| | Cloudflare Tunnel → Mac mini | 境外云主机 + 自有域名 |
|---|---|---|
| 备案 | 不需要 | 不需要 |
| 成本 | 0（域名 ~¥70/年） | ~$5–10/月 + 域名 |
| 上手 | 半小时 | 半天（迁移 + 部署） |
| 入站端口 | 不需要（纯出站连接） | 需要，多一层攻击面 |
| **家宽依赖** | **强——断网 / 重启 / 停电即中断** | 无 |
| **300 人峰值** | **家宽上行 + NAT 并发数是隐忧** | 可控 |
| 数据位置 | 全在自己机器（隐私更好） | 在云上 |
| 迁移成本 | 无 | Node + SQLite + activity pack 都要搬 |

## 5. 但真正的风险不在基建选择上

300 人 = **300 个独立 bot 绑定**，每个绑定一条长轮询（`getupdates` 40s 超时）。
两个未验证风险的权重远大于"隧道还是云主机"：

**R1. iLink 是否允许一台机器维持几十上百个绑定？—— 已解除最小情形，规模仍未知**

2026-08-03 实测：**2 个绑定可以共存、消息不串台**（findings §4）。
协议层面不禁止一机多绑定，这是 v3 得以成立的基础。

但官方定位仍是"个人助手、尚未开放为第三方 Bot 平台"，
**2 个能过不代表 30 个能过**，300 个正是最可能撞限流的量级。规模上限是当前最大未知。

低成本的先行探测：批量请求二维码但**不扫**，测「服务端允许同时存在多少个待确认会话」
——这个数往往是绑定数上限的先行指标，且不需要几十个微信号。

**R2. 微信内置浏览器是否放行你的域名？—— 已部分验证 ✅（2026-08-01）**

实测 `https://<随机>.trycloudflare.com` 在微信内**直接打开，无警告页、无拦截**。

结构性结论：**微信内置浏览器不要求域名备案**——免备案的境外域名在微信里能正常访问。
这解除了整个「免备案路线」在浏览器层面的根本疑虑。

但"通过"的边界要说清楚，以下**不能**由这次结果推出：

- 测的是**空白页面**（只返回 `tunnel ok`）、**零流量**、**未被分享进群**。
  微信的拦截很大程度上是**基于举报与流量特征的动态行为**，不是静态域名白名单。
  一个承载真实报名页、被转进 300 人群、短时间大量点击的链接，可能触发不同判定。
- `*.trycloudflare.com` 是**多人共用的公共域名**，被他人滥用会连累你，
  且可能在毫无预警的情况下随时被封——对有固定日期的活动是不可接受的风险。

⇒ B 步仍应使用自有域名，但理由变了：不再是"怕微信不放行免备案域名"（已证伪），
而是**共享域名的声誉风险 + quick tunnel 的 URL 每次重启都变**。

**任一不通过，选哪种基建都没有意义。** 因此不要在这两项之前投入基建成本。

## 6. 三步走

### A. 现在（免费，零承诺）

> 原计划把"打通隧道"和"验证多绑定"混在一步，实际上二者**互相独立**：
> 验证多绑定不需要隧道（两台手机站在电脑前扫本地终端上的码即可），
> 远程访问是 B 步才需要的东西。故拆为 A1 / A2。

#### A1. 打通 cloudflared —— ✅ 已完成（2026-08-01）

```bash
brew install cloudflared
# 起一个临时测试服务（不要用 3000，那是真 dashboard）
node -e "require('node:http').createServer((q,s)=>s.end('tunnel ok')).listen(8787)"
cloudflared tunnel --url http://localhost:8787
```

结果：

- 公网可达，HTTP 200 ✅
- **微信内直接打开，无警告无拦截** ✅（见 §5 R2）
- 隧道连接落在 **新加坡节点**（`location=sin21` / `cf-ray: ...-SIN`），
  实测印证了免费版无中国节点——国内流量走跨境路径，
  **延迟与稳定性不由 Cloudflare 优化**，300 人并发时这是真实变量

#### A2. 验证多绑定 —— ✅ 已完成（2026-08-03）

`node scripts/probe-dual-binding.mjs`，两个真实微信号各自扫码：

- Q1 两个绑定共存 ✅（B 接入未顶掉 A，全程零异常）
- Q2 消息路由无串台 ✅（两边 `userId` 完全不重叠）
- 附带查明：同一微信号再次扫码会顶掉自己的旧绑定 ⇒ v3 需回收僵尸实例

⇒ **R1 的最小情形已解除**，但规模上限（§5 R1）仍未知。
详见 `multi-binding-findings.md` §4。

### B. A 通过后（一个下午 + 一个域名）

Cloudflare Tunnel + 自有域名（境外注册，Cloudflare Registrar 即可），
named tunnel 拿到稳定主机名。

- 目标：**拉群里 10–20 个人真实试一次**
- 覆盖风险：**R1（20 个绑定）+ R2（微信放行）一次性都验**
- 仍然零服务器、零备案
- **这一步是整个决策的分水岭**

> **具体操作清单已单独成文**（含自愈配置、隧道、验证、巡检、收尾）：
> - `docs/deploy-mac-mini.md` —— 方案 A：Mac mini + launchd 自愈 + 固定域名
> - `docs/deploy-cloud.md` —— 方案 B：境外云主机 + systemd
>
> 两者的决定性分歧是**微信风控**：家宽 IP 与测试环境一致，数据中心 IP 是未知数。
> 无论选哪个，上线前都必须先跑 `scripts/probe-dual-binding.mjs`。

### C. 只有 B 通过、且确定要办 300 人（~$5–10/月）

迁到境外云主机（香港 / 新加坡）。

- **迁移理由不是备案，是可靠性**——不要把 300 人的活动押在家宽和一台
  可能被随手重启的 Mac mini 上
- 迁移内容：Node 运行时 + SQLite + activities/ + 隧道或直接公网入口

## 7. 结论

**先隧道，现在不要买云主机。**

触发迁移的条件是「B 步验证通过 + 确定要跑真实规模」，而不是"公网暴露"这件事本身。
B 步的 20 人测试花一个下午，能省掉可能白买的服务器和白办的备案。

## 8. 执行顺序上的依赖

```
A1 隧道打通 + 微信放行     ✅ 已完成（2026-08-01）
        │
        ├─ R2 已部分解除（微信不要求备案域名）
        ↓
A2 / findings §4 双绑定验证（需第二个微信号）   ← 当前阻塞点
        ↓ 通过
   B 步：自有域名 + 20 人真实测试   ← 分水岭（同时压 R1 与 R2 的真实场景）
        ↓ 通过且确定规模
   C 步：迁境外云主机
```

在 A2 出结果前，**B 步之后的都不要动**。

### 另一件必须排在 B 步之前的事

**dashboard 目前无任何鉴权**，四个路由全部裸奔：

| 路由 | 暴露内容 | 风险 |
|---|---|---|
| `/api/status` | `qrUrl`（**bot 登录二维码**） | 🔴 他人可抢先扫码，把 bot 绑到自己微信 |
| `/api/users` | 全部报名数据（姓名、微信号） | 🔴 参与者个人信息泄露 |
| `/api/qrcode?url=` | 任意 URL 渲染成二维码 | 🟡 可被当作钓鱼图床 |
| `/` | 控制台页面 | 🟡 |

它从设计之初就是 localhost-only。**任何"真暴露"之前必须先加鉴权**，
并且要把「参与者页面」与「运营者控制台」拆成两个独立的暴露面
（前者公开，后者永不公开或强鉴权）。A 步不受影响，因为 A 步不暴露它。
