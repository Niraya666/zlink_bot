# 评议报名者

读 `activities/<slug>/rubric.md` 和导出的报名数据，产出一份评议记录。

**这个 skill 不输出名单。** 它输出候选组合、每套组合的塌陷风险、
以及每个落选者一句可被反驳的理由。名单由组织者定。

## 前置

需要 `activities/<slug>/rubric.md`。没有就先跑 `design-rubric` skill。

⚠️ 如果 rubric 的生成时间**晚于**报名数据，在最终产出里显著标注：
这份评议能证明「依据可复核」，不能证明「没有偏向」。不要让用户误以为它能。

导出数据：

```bash
node cli.js export <slug> > /tmp/signups.json
```

## 四个必须停下来问的地方

这个 skill 的价值一半在判断，一半在**知道哪些不该自己判**：

| # | 停顿点 | 为什么不能自己定 |
|---|---|---|
| 1 | 争议入池 | 内容厚但流程没走完的人，留不留是组织者的风险偏好 |
| 2 | 约束数值调整 | 如果硬约束在真实数据上无解，是放宽约束还是接受缺口，是活动设计决策 |
| 3 | 画像缺口 | 「某一类人没报名」是招募渠道问题，塞进筛选逻辑会变成硬凑类别 |
| 4 | 最终名单 | 永远是组织者的 |

每个停顿点都要**把依据摆出来再问**，不要只问「你觉得呢」。

## 流程

### 1. 入池判定

按 rubric §0 硬条件 + §1 入池闸筛。

**不要用报名状态字段筛。** 对话可能在任何一轮中断：
状态「已完成」只说明必收字段收齐了，不说明内容有价值；反过来，
内容最厚的人可能因为聊得太深、把话题拐走，反而没走完登记流程。

产出一张表：谁入池、谁不入、每人一句理由。

**排除承担其他角色的人**（主持人、领航员、组织者本人）——
他们不占参与席位。这一步容易漏，漏了会让整个池子的数目算错。

**争议入池**单独列出来问用户（停顿点 1）。典型情况：
只差一个纯登记字段（能否参加、联系方式）。这类应该转成
「待确认清单」私下补问一句，而不是当资格门槛。

### 2. 匿名评议

**这一步隐藏姓名和昵称**，只喂自由文本字段。

熟人社群里这条不是形式主义：不匿名的话，rubric 只是把既有印象
固化成看起来客观的分数。

对每个入池者产出：

- **议题燃料**：对照 rubric §2，每个议题标 强 / 中 / 弱 / 无，**必须引原文片段**
- **画像归类**：对照 rubric §3 的类别（用文案的原话，不要另造标签）
- **立场**：顺着主题前提 / 质疑前提。质疑的具体质疑什么
- **一句独有贡献**：这个人能在桌上说出什么别人说不出的，带引文
- **一句风险**：可能带偏话题、可能不发言、内容与某人高度重合……

### 3. 覆盖检查 —— 先于任何取舍

把 rubric §2–§4 的约束拿真实数据核一遍，**在挑人之前**：

- 每个议题的亲历者够不够保底人数
- 每个画像类别有没有人
- 立场分布满不满足

**出现缺口就停下来**（停顿点 3）。缺口不是筛选能解决的问题，
选项是：定向补人 / 接受并在现场说明 / 调整议程。这是活动设计决策。

一个典型且容易被忽略的缺口：讨论的**对象**缺席。
比如主题是「新人怎么成长」，一桌全是带过人的和转过型的，
没有一个新人能当场说「不是这样的」。这类缺口要显式报出来。

如果约束在真实数据上根本无解，报出来问用户（停顿点 2），
不要自己悄悄放宽。

### 4. 组合方案

先让约束把答案逼出来，再看还剩多少自由度：

1. 被约束锁定的人（拿掉就有议题塌）—— 直接列出，说明为什么锁定
2. 剩余席位在剩余候选里排列
3. 给 **2–3 套**方案，每套写清：**张力来自哪里** + **塌陷风险是什么**

塌陷风险的例子：「三个人都在质疑前提，可能整场变成对文案的批判会」、
「除 X 外没人有实操经验，讨论会停在概念层」。

**不要给唯一答案。** 如果约束把答案完全锁死了，说明约束设得太紧或候选太少，
如实告诉用户，而不是假装这是筛选的结果。

### 补选：按覆盖角色，不排顺位

如果用户要备选（几乎总是要——有人鸽是常态），**不要给一条顺位队列**。

「顺位」隐含个人排序，而整套 rubric 建立在组合约束上。正选里某个人退出时，
按顺位递补上来的可能完全不覆盖他所满足的约束——**约束当场破掉，
而流程看起来一切正常**。

每个补选要标注「可替补谁、覆盖哪条约束」。然后做一次**故障检查**：

> 逐个假设正选里的每个人退出，看补选里有没有人能接上他覆盖的约束。

接不上的那条要显式报出来。这是最容易被 6＋2 这种安排掩盖过去的风险：
数字上有备选，实际上没有。

### 池子接近席位数时

若入池人数 ≈ 席位数 + 补选数，说明 rubric 实际上没有排除任何人。
**如实说出来**：过滤发生在漏斗，不在 rubric。此时它的产出是
「谁先上、谁补谁」，不是「谁进」。不要包装成筛选结果。

### 5. 落选理由

每个落选者一句，标准只有一条：**组织者要能一眼判断这句话对不对**。

| ❌ 不可反驳 | ✅ 可反驳 |
|---|---|
| 「综合分 3.2，排第 7」 | 「与 X 的经历高度重合，而 X 讲得更具体」 |
| 「匹配度不足」 | 「带来的是一个想找人参与的项目，不是一段经历或一个困惑」 |
| 「表达不够清晰」 | 「两个议题都只有观察没有亲历，A 议题已有 3 位亲历者」 |

理由要能溯源到 rubric 的某一条，而那一条又溯源到公开文案。
链条断了说明 rubric 有问题，回头改 rubric，不要在这里临时发明理由。

### 6. 两份产出

**内部评议记录** `data/review-<slug>.md`（含姓名、引文、落选理由）——
不要公开，含个人信息和对真人的直接评价。

**可公示摘要**（用户要的话再生成）——脱敏，只含：

- rubric 全文（它本来就该是公开的）
- 池子规模、入池标准、各约束的满足情况
- 缺口与处置说明

**不含**任何个人的评价、引文、落选理由。

「证明选人不是拍脑袋」靠的是公开**方法和约束**，不是公开对每个人的评价。
后者只会伤人，而且没有人授权你这么做。

## 常见错误

- **用状态字段筛人** —— 会静默丢掉内容最厚的候选
- **先排序再套约束** —— 顺序反了。约束先跑，排序只用于剩余自由度
- **给空的可选字段扣分** —— 那是采集没问到，不是候选人说不出来。
  检查一下该字段的整体缺失率，大面积为空就是 flow.md 的问题
- **为凑类别硬塞人** —— 缺口该报出来让人处理，不是用低质量候选填上
- **agent 直接给名单** —— 越界。给依据，不给决定
