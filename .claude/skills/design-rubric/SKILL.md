# 设计选人 rubric

为一场**席位有限**的活动生成 `activities/<slug>/rubric.md`，
并反过来检查 `fields.json` / `flow.md` 能不能支撑它。

## 什么时候跑

**建完活动 pack、开始招募之前。** 不是收完报名之后。

顺序不是形式问题。报名后才写的 rubric，每一维都可能是为已有人选倒推的——
尤其当报名者是熟人时。rubric 先于报名，`git log` 就是证据。

已经收完数据才来补 rubric：照跑，但**必须在文件头标注「事后补写」**，
并且不要让用户以为它能证明「没有偏向」。它只能证明「依据可复核」。

## 适用与不适用

适用：席位有限、有公开招募文案、**一桌人的组合质量比单人质量更重要**
（圆桌、工作坊、共创、小规模共学）。

不适用，别硬套：
- 招聘、录取 —— 有法律与流程要求，个人资质本身就是标的
- 抽奖、先到先得 —— 本来就不该有 rubric
- 报名人数远超席位（比如 300 选 6）—— 那是漏斗问题，先做粗筛再谈组合

## 六条元规则（跨活动固定，不要重新发明）

这些是从真实失败里提取的，每场重新生成只会把它们弄丢：

1. **溯源约束** —— 每一个维度必须能引用招募文案里的一句原文。
   引不到就不准进 rubric。这一条同时防住两件事：LLM 编出一堆看着合理的维度，
   以及落选理由无法被参与者本人检验。

2. **每一维必须绑定数据来源** —— 指明它读哪个字段、或读哪段自由文本。
   绑不上就说明字段缺了（回到步骤 4），或者这一维根本不该存在。

3. **硬条件 ≠ 评分维度** —— 「能全程参与」这类是入池闸（满足/不满足），
   不是分数。混进评分会让一个纯排期问题吃掉内容判断的权重。

4. **组合约束优先于个人排序** —— 个人分最高的 N 个人不等于最好的 N 人组合。
   只做个人排序的 rubric 会系统性选出同质化的一桌人。

5. **空的可选字段是采集问题，不是候选人的问题** —— 某个可选字段大面积为空，
   说明 flow.md 没问到，不该由候选人承担。这种情况要么把字段升为必收，
   要么降低该维度权重，而不是给空着的人扣分。

6. **评分阶段隐藏身份** —— 姓名、群昵称在评分时不参与，组合阶段再接回来。
   熟人社群里这条尤其重要，否则 rubric 只是把既有印象固化成分数。

## 流程

### 1. 拿到招募文案

**这是必需输入**，没有就停下来问。rubric 的合法性全部来自它。

同时读 `activities/<slug>/` 下已有的 `activity.json` / `fields.json` / `flow.md`。

### 2. 从文案里抽三样东西

只抽，不发挥：

- **席位结构** —— 总人数、角色构成（主持人 / 领航员 / 参与者各几名）。
  注意排除不占参与席位的角色。
- **公开画像** —— 文案里「欢迎这些朋友」之类的段落。**这就是画像类别，
  不要另外发明标签**。组织者已经公开承诺了，照抄即可。
- **议程结构** —— 文案里列出的话题 / 环节。每个话题需要什么样的亲历者才烧得起来。

抽完向用户复述一遍，确认没漏没歪。

### 3. 派生维度

每一维写成一行，必须带上原文出处：

```
维度：GAP 亲历
出处：「正在经历或曾经经历过 GAP，愿意分享真实感受、行动与困惑」
来源：background 自由文本
```

引不到原文的维度**当场丢掉**，并告诉用户丢了什么、为什么。

常见的引不到的例子：「可靠性 / 守约记录」（文案里通常没有，且没人会自述鸽过）、
「影响力」「资历」（除非文案真的写了）。

### 4. 反查字段覆盖 —— 这一步是本 skill 的主要价值

拿派生出的维度逐一去对 `fields.json` 和 `flow.md`：

| 情况 | 处置 |
|---|---|
| 维度有对应的必收字段 | ✅ |
| 维度只有可选字段撑着 | ⚠️ 提议升为必收，或在 flow.md 里改成必问 |
| 维度没有任何字段/话术支撑 | ❌ 要么加字段，要么删掉这一维 |

**把修改建议直接给出来**（具体到改哪个文件的哪一行），让用户决定改不改。

这一步之所以关键：收完数据再发现字段不够，就永远补不上了。

### 5. 定组合约束 —— HITL

根据议程结构和画像类别，提议硬约束，**数值必须让用户拍板**：

- 每个话题的亲历者保底人数（「B 话题至少 3 人有真实经历」）
- 画像类别的覆盖下限与单类上限
- 是否需要立场分布约束（见下）

**立场约束值得单独提**：如果活动主题带有一个默认前提
（「XX 正在消失」「YY 是好事」），要问用户是否加一条
「最终名单中至少 N 人对这个前提本身持异议」。

没有反方的圆桌不是讨论，是共识确认会。而按「具体性 / 亲历度」打分时，
异见者常常因为表达抽象或跑题而失分——rubric 会亲手清洗掉自己想要的张力。

### 6. 写 `activities/<slug>/rubric.md`

模板：

```markdown
# <活动名> · 选人 rubric

> 生成于 <YYYY-MM-DD>，早于招募开始（可用 git 提交时间与报名 created_at 核对）
> 依据：<招募文案的出处>
> 席位：<角色构成>，需要筛选的是 <N> 席

## 0. 硬条件（不打分，不满足即出局）

- <条件> —— 出处：「<文案原文>」

## 1. 入池闸

<什么样的报名算「有内容」，可以进入评议>

⚠️ 入池判定**不看报名状态字段**。对话可能在任何一轮中断，
状态不完整不代表内容不足；反过来内容最厚的人可能恰恰因为聊得太深而没走完流程。

## 2. 议题燃料

| 议题 | 需要什么样的亲历 | 数据来源 | 保底人数 |
|---|---|---|---|

## 3. 画像覆盖

| 类别 | 文案原文 | 下限 | 上限 |
|---|---|---|---|

## 4. 立场分布

<异见约束，或写明「本场不设」>

## 5. 平局裁决

**只在 §2–§4 全部满足后仍需取舍时才用。** 维度：

| 维度 | 分档 | 数据来源 | 出处 |
|---|---|---|---|

## 6. 已知不覆盖

<哪些想评但没有数据源的东西，以及为什么放弃>

## 7. 复盘待验

<跑完这场之后要回头检查什么>
```

### 7. 收尾提示

告诉用户两件事：

- **建议把 `rubric.md` 随招募文案一起公开。** 报名者事先知道标准，
  落选时才有可复核的依据。这也是这份 rubric 唯一能证明「没有偏向」的方式。
- 报名结束后用 `select-participants` skill 跑评议。

## 常见错误

- **发明文案里没有的维度** —— 最高频的失败。宁可 rubric 只有三维，
  也不要凑出五维。
- **把 rubric 写成打分表** —— 主体应该是约束（§2–§4），分数只是平局裁决。
- **为了「客观」而结构化一切** —— 「具体性」「有没有未解的张力」这类
  故意不设字段，让评议时直接读自由文本原文。LLM 读原文比读标签准得多，
  而且多一个字段就多一轮对话，报名完成率会掉。
- **把两个用途不同的字段合并评分** —— 「与主题的连接」决定入池，
  「愿意带来什么」决定现场排布。合并会把「背景极扎实但带来的问题跑题」的人
  压成中间值，两头都不对。
